# GoStudy — технический аудит неплатёжной части

Дата: 20 сентября 2026 года.  
Основа аудита: приложенный архив `gostudy-main (9)(1).zip` и документация
проекта.  
Область: React/Vite, NestJS/TypeScript, Prisma/PostgreSQL, авторизация,
профили, родители и дети, расписание, класс, задания, материалы, сообщения,
уведомления, отзывы и административные модули.

Оплаты, банковские карты, эквайринг, выплаты и изменение их бизнес-логики в
аудит не входили.

## Итог

Критические дефекты неплатёжной части исправлены. Активный frontend больше не
вызывает legacy PHP API. Самостоятельная регистрация ученика требует точную
дату рождения и разрешена только с 18 лет; несовершеннолетнего создаёт
родитель из своего кабинета. Чистая установка backend теперь сама генерирует
Prisma Client, а отдельная проверка компилирует полный DI-граф NestJS.

После изменений успешно прошли:

- чистая установка frontend и backend через `npm ci`;
- frontend ESLint и production build;
- backend TypeScript check и NestJS build;
- 53 test-файла и 213 тестов;
- компиляция полного графа NestJS-модулей;
- offline-проверка production-зависимостей npm: 0 известных уязвимостей в
  доступной локальной базе advisory.

## Модульность

В backend выделено 35 NestJS-модулей. Контроллеры в основном тонкие, DTO
проверяются глобальным `ValidationPipe`, инфраструктура файлов, Prisma,
security-token и календарная логика вынесены в `common`. Межмодульные
зависимости объявляются через Nest `imports`/`exports`; полный граф после
изменений компилируется.

В текущем исправлении модульность усилена точечно, без рискованного
переписывания рабочих областей:

- единый модуль возрастных правил вместо локальных реализаций;
- отдельный DTO и публичные методы NotificationsService для настроек ученика;
- отдельные scripts для генерации Prisma и проверки DI-графа;
- удаление общего legacy PHP-слоя из React API-клиента;
- удаление неиспользуемых модулей.

### Оставшийся архитектурный долг

Следующие пункты не ломают текущую сборку, но повышают стоимость изменений:

1. Крупные сервисы: `homework.service.ts` — около 1235 строк,
   `profile.service.ts` — 979, `classroom.service.ts` — 941,
   `journal.service.ts` — 889, `messages.service.ts` — 888. Их стоит делить
   по use case: query, command, access policy, serialization и file workflow.
   Делать это лучше по одному модулю с контрактными тестами, а не массовым
   рефакторингом.
2. В административных и сериализующих слоях остаются `Record<string, any>` и
   динамические Prisma-delegate. Следующий безопасный шаг — типизированные
   response-модели и узкие интерфейсы для общих операций.
3. Несколько областей импортируют конкретные сервисы соседнего модуля. DI-граф
   сейчас корректен, но при дальнейшем росте лучше выносить междоменные порты
   и события, чтобы не создавать циклы.
4. Во frontend есть крупные компоненты: справочник подготовок, мастер анкеты
   преподавателя, карточка преподавателя и анкета ученика. Их следует делить
   по состоянию формы и визуальным секциям после появления компонентных
   тестов.

## Проверенные контуры

### Авторизация и доступ

- роли регистрации определяются сервером;
- пароли хешируются bcrypt, сеансовые и почтовые токены хранятся как SHA-256;
- защищённые пользовательские маршруты используют SessionAuthGuard,
  административные — дополнительную проверку роли;
- глобальная валидация запрещает лишние поля DTO;
- Helmet и CORS включены;
- реальные `.env`, приватные ключи и очевидные секреты в архиве не найдены.

Открытый риск: общего rate limit для login, регистрации и восстановления
пароля нет. Ограничение повторной отправки email реализовано бизнес-правилом,
но инфраструктурный limiter следует проектировать с учётом reverse proxy и
нескольких экземпляров API; в этот патч новая инфраструктура не добавлялась.

### Данные и файлы

- изменения Prisma оформлены отдельной расширяющей миграцией;
- приватное файловое хранилище нормализует имена, ограничивает размер и тип,
  проверяет сигнатуры и выход за допустимый каталог;
- транзакционные операции сохранены;
- удаляющих либо преобразующих существующие данные миграций не добавлено.

Ограничение проверки: миграция не применялась к реальной PostgreSQL-базе,
потому что в архиве нет рабочего подключения. Перед выпуском обязательны
backup, `prisma migrate deploy` в staging и smoke-проверка на копии данных.

### Уведомления и PHP

В активных исходниках React нет `.php`, `LEGACY_API` и `isLegacyApiUrl`.
Исторические материалы в `docs/api` и `HOST_API` оставлены как спецификация;
`public/404.php` и `public/sitemap.php` являются отдельными deployment-
артефактами, а не API. Они не включаются в пользовательские запросы к данным.

Новый student-settings endpoint сохраняет предпочтение будущей отправки писем
родителю. Фактическая событийная email-доставка ещё не реализована, что явно
зафиксировано в документации и не маскируется как завершённая функция.

### Клиент и производительность

Production build разделяет страницы и тяжёлые просмотрщики на чанки. Самые
крупные ожидаемые артефакты — worker PDF.js (около 1.26 MB без gzip) и PDF-
chunk (около 425 KB, около 127 KB gzip). Это не блокирующий дефект, поскольку
они загружаются отдельно, но размер стоит контролировать бюджетом сборки.

Автоматических unit/component-тестов frontend в проекте нет; доступные
проверки — ESLint и production build. Критические правила регистрации поэтому
дублируются только для UX, а окончательно исполняются и тестируются на сервере.

## Перед развёртыванием

1. Сделать backup PostgreSQL и файлового хранилища.
2. Выполнить `npm ci` в корне и `server`.
3. Настроить `server/.env`, SMTP и каталоги загрузок.
4. Выполнить `npm --prefix server run prisma:migrate:deploy`.
5. Повторить lint, тесты, build и `npm --prefix server run test:modules`.
6. Провести staging smoke-test: совершеннолетний ученик, запрет
   несовершеннолетнего, создание ребёнка родителем, подтверждение email,
   настройки уведомлений ученика, документы/видео преподавателя и
   административная модерация.

Платёжные сценарии в этот checklist намеренно не включены.
