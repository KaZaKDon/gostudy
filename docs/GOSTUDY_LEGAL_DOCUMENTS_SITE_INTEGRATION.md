# GoStudy: размещение юридических документов на сайте

**Назначение:** техническая инструкция для интеграции юридических документов в React + Vite,
NestJS, Prisma и PostgreSQL.  
**Редакция:** 1.1  
**Дата актуализации:** 30 августа 2026 года  
**Статус:** рабочее техническое задание.

> SQL-примеры, оставшиеся в расширенных разделах документа, были составлены
> для прежней MySQL-версии и используются только как описание требуемых полей.
> Они не выполняются. Актуальная исполняемая схема находится в
> `server/prisma/schema.prisma` и миграциях Prisma.

## 1. Цель

На сайте должна работать единая система юридических документов, которая:

- показывает каждый документ по постоянному адресу;
- загружает текст из отдельного Markdown-файла;
- хранит номер редакции и дату начала действия;
- сохраняет точную редакцию, принятую пользователем;
- не позволяет незаметно заменить уже принятый текст;
- разделяет обязательные документы и добровольные согласия;
- поддерживает отдельные согласия Родителя для каждого детского профиля;
- позволяет отозвать рекламное согласие без удаления аккаунта;
- после заполнения реквизитов ИП и сведений о сервере не требует переделки кода.

## 2. Главный принцип хранения

### 2.1. Рабочие и опубликованные файлы

Рабочие черновики и опубликованные документы не смешиваются.

```text
storage/legal/
├── drafts/
│   └── рабочие версии, которые не показываются пользователям
├── current/
│   └── действующие версии документов
└── archive/
    └── неизменяемые копии всех опубликованных редакций
```

Рекомендуемая структура архива:

```text
storage/legal/archive/
├── privacy-policy/
│   ├── 1.0.md
│   └── 1.1.md
├── platform-rules/
│   └── 1.0.md
└── marketing-consent/
    ├── 1.0.md
    └── 1.5.md
```

После публикации архивный файл не изменяется. Новая редакция создаётся новым файлом с новым
номером.

### 2.2. Где хранить файлы

Канонические опубликованные файлы хранятся в `shared/legal` и размещаются на российском сервере вместе с NestJS API,
но вне каталога, из которого веб-сервер раздаёт файлы напрямую. Пользователь получает документ
через контролируемый API.

Это позволяет:

- обновлять текст без новой сборки React;
- проверять действующую редакцию на сервере;
- вычислять контрольную сумму на сервере;
- хранить архив принятых редакций;
- не доверять номеру редакции, присланному браузером.

В React допускаются временные демонстрационные тексты, но они не должны становиться единственным
источником опубликованного документа.

|---|---|

| Политика конфиденциальности | `/legal/privacy` |
| Правила платформы | `/legal/rules` |
| Согласие на обработку персональных данных | `/legal/personal-data-consent` |

## 5. Рекомендуемая структура фронтенда

```text
src/
├── pages/
│   └── legal/
│       └── LegalDocumentPage.jsx
├── components/
│   └── legal/
│       ├── LegalDocumentHeader.jsx
│       ├── LegalDocumentContent.jsx
│       ├── LegalDocumentStatus.jsx
│       └── LegalDocumentError.jsx
├── api/
│   └── legalApi.js
├── config/
│   └── legalDocuments.js
└── styles/
    └── legal.css
```

Один компонент `LegalDocumentPage` обслуживает все адреса. Текст документа не вставляется прямо
в JSX.

Компонент должен:

- определить ключ документа по маршруту;
- запросить документ у API;
- показать название, редакцию и дату действия;
- отобразить Markdown;
- показать состояние загрузки и понятную ошибку;
- позволить распечатать документ;
- корректно работать на мобильном экране;
- иметь собственную прокручиваемую область, если этого требует макет GoStudy.

Для Markdown можно использовать `react-markdown` и `remark-gfm`. Не подключать обработку сырого
HTML из Markdown без отдельной необходимости и очистки.

## 6. Реестр документов

На сервере нужен реестр, связывающий ключи, файлы, адреса и действующие редакции. Его можно
хранить в таблице базы данных. Файл конфигурации допустим только как начальный вариант.

Минимальные поля реестра:

```text
id
document_key
title
public_path
current_version
current_hash
current_file_path
effective_from
status
acceptance_type
requires_reacceptance
created_at
updated_at
```

Допустимые значения `status`:

```text
draft
scheduled
active
archived
```

Примеры `acceptance_type`:

```text
notice_only
required_registration
optional_marketing
parent_per_child
offer_acceptance
```

## 7. История редакций

Отдельная таблица `legal_document_versions`:

```text
id
document_id
version
content_hash
file_path
effective_from
published_at
published_by
change_summary
requires_reacceptance
created_at
```

Правила:

1. Контрольная сумма вычисляется сервером по алгоритму SHA-256.
2. Браузер не определяет контрольную сумму самостоятельно.
3. Опубликованная версия не перезаписывается.
4. Новая редакция получает новый номер и новую архивную копию.
5. Предыдущая редакция остаётся доступной для проверки согласия.
6. Техническая правка без изменения смысла всё равно фиксируется как отдельная версия, если
   изменился опубликованный текст.

## 8. API юридических документов

Рекомендуемые обработчики:

```text
GET  /api/v1/legal/documents/:key
GET  /api/v1/legal/documents
POST /api/v1/legal/acceptances
POST /api/v1/legal/acceptances/:id/withdraw
GET  /api/v1/legal/acceptances/me
GET  /api/v1/legal/unsubscribe?token=...
POST /api/v1/legal/unsubscribe
```

Обработчик `GET /api/v1/legal/documents/:key` возвращает:

```json
{
  "success": true,
  "document": {
    "key": "marketing_consent",
    "title": "Согласие на получение информационных и рекламных сообщений GoStudy",
    "version": "1.5",
    "hash": "sha256:...",
    "effectiveFrom": null,
    "status": "draft",
    "content": "# Согласие..."
  }
}
```

До публикации API не должен отдавать черновик обычному пользователю. Черновики доступны только
администратору с соответствующим правом.

## 9. Фиксация юридически значимого действия

Одна галочка может ссылаться на несколько документов. Поэтому лучше хранить событие действия и
отдельно связывать его с редакциями документов.

### 9.1. Таблица событий

`legal_action_events`:

```text
id
user_id
action_type
checkbox_text
email_at_action
subject_profile_id
occurred_at
ip_address
user_agent
request_id
email_verified_at
created_at
```

Примеры `action_type`:

```text
accepted
accepted_pending_email
activated_after_email_confirmation
withdrawn
offer_accepted
parent_consent_given
parent_consent_withdrawn
```

`subject_profile_id` заполняется, когда Родитель даёт согласие в отношении конкретного ребёнка.

### 9.2. Документы события

`legal_action_event_documents`:

```text
id
event_id
document_key
document_version
document_hash
document_title
created_at
```

При общей обязательной галочке одно событие связывается сразу с Пользовательским соглашением,
Правилами платформы и Политикой конфиденциальности.

### 9.3. Текущее состояние добровольного согласия

Для быстрой проверки рекламной рассылки нужна таблица `user_consent_states`:

```text
id
user_id
consent_key
email
status
accepted_event_id
activated_event_id
withdrawn_event_id
updated_at
```

Возможные состояния рекламного согласия:

```text
not_given
pending_email_confirmation
active
withdrawn
suspended_email_changed
terminated_account_deleted
```

Журнал событий не заменяется текущим состоянием и не удаляется при изменении флага.

## 10. Галочки регистрации

На регистрации показываются три отдельные, заранее не отмеченные галочки.

### 10.1. Обязательная галочка документов

```text
Я принимаю Пользовательское соглашение и Правила платформы и подтверждаю,
что ознакомился с Политикой конфиденциальности.
```

Слова с названиями документов являются отдельными ссылками.

### 10.2. Обязательная галочка персональных данных

```text
Я даю согласие на обработку персональных данных.
```

Фраза «согласие на обработку персональных данных» открывает полный отдельный документ.

### 10.3. Необязательная рекламная галочка

```text
Я согласен получать новости, специальные предложения и рекламные сообщения
GoStudy по электронной почте.
```

Галочка не влияет на возможность регистрации.

### 10.4. Поведение формы

- Все галочки пустые при первом открытии.
- Кнопка регистрации недоступна без первых двух галочек.
- Третья галочка необязательная.
- Переход по ссылке на документ не отмечает галочку автоматически.
- Версии и контрольные суммы документов загружаются до отправки формы.
- Сервер повторно проверяет, что браузеру были показаны действующие редакции.
- При смене редакции во время заполнения формы сервер возвращает требование перечитать документ.
- Для несовершеннолетнего детского профиля рекламная галочка не показывается.
- Родитель может согласиться на рекламу только для собственной подтверждённой почты.

## 11. Регистрация и подтверждение электронной почты

Рекомендуемый порядок:

1. Фронтенд получает текущие редакции документов.
2. Пользователь отмечает обязательные галочки и при желании рекламную.
3. Форма отправляет выбранные действия и показанные версии.
4. Сервер проверяет редакции по собственному реестру.
5. Сервер создаёт пользователя и сохраняет события принятия документов.
6. Рекламное согласие сохраняется со статусом `pending_email_confirmation`.
7. Пользователь подтверждает электронную почту.
8. Сервер создаёт событие `activated_after_email_confirmation` и переводит рекламное согласие в
   состояние `active`.
9. До восьмого шага рекламные письма не отправляются.

## 12. Несовершеннолетние и Родитель

- Несовершеннолетний не завершает самостоятельную регистрацию без подтверждённого Аккаунта
  Родителя.
- Детский профиль не получает собственную рекламную галочку.
- Рекламные письма непосредственно ребёнку не направляются.
- Родительское согласие на обработку данных оформляется отдельно для каждого детского профиля.
- В событии родительского согласия сохраняются `parent_user_id` и `subject_profile_id`.
- Согласие по одному ребёнку не распространяется на другого.
- Отзыв родительского согласия по одному профилю не меняет состояние других детских профилей.

## 13. Отписка от рекламных писем

Каждое рекламное письмо содержит ссылку с безопасным токеном.

Рекомендуемый поток:

1. Пользователь переходит по ссылке без входа в аккаунт.
2. Сервер проверяет срок и подлинность токена.
3. Открывается страница подтверждения адреса рассылки в замаскированном виде.
4. После подтверждения отправляется POST-запрос на отписку.
5. Создаётся событие `withdrawn`.
6. Состояние меняется на `withdrawn`.
7. Адрес добавляется в список запрета рассылки.

Токен нельзя хранить в базе в открытом виде. В базе хранится его хеш. В адресе ссылки не должны
находиться ФИО, открытый email или идентификатор ребёнка.

Отказ от рекламы не прекращает служебные письма:

- подтверждение электронной почты;
- восстановление пароля;
- безопасность аккаунта;
- заявки, расписание и уроки;
- платежи, возвраты и выплаты;
- юридически значимые уведомления.

## 14. Список запрета рассылки

Нужна отдельная таблица `marketing_suppression`:

```text
id
user_id
email_hash
reason
source_event_id
created_at
released_at
release_event_id
```

Перед каждой рекламной отправкой проверяются одновременно:

- подтверждение электронной почты;
- состояние `active`;
- отсутствие адреса в списке запрета;
- совершеннолетний получатель;
- совпадение адреса с адресом, для которого дано согласие.

Повторное включение допускается только после нового добровольного согласия и создаёт новое
событие. Старое событие отзыва не удаляется.

## 15. Изменение электронной почты

При смене email:

1. рекламная рассылка на старый адрес прекращается;
2. состояние меняется на `suspended_email_changed`;
3. новый адрес подтверждается;
4. пользователю показывается новая добровольная рекламная галочка;
5. согласие со старого адреса автоматически не переносится;
6. новое согласие фиксируется новым событием.

## 16. Публикация новой редакции

Административный сценарий публикации должен выполнять следующие действия как одну операцию:

1. Проверить наличие обязательных метаданных.
2. Вычислить SHA-256 файла.
3. Скопировать файл в каталог архива с номером редакции.
4. Создать строку в `legal_document_versions`.
5. Назначить действующую редакцию в реестре.
6. Обновить файл в `current`.
7. Записать администратора, дату и описание изменений.
8. Определить, требуется ли повторное принятие.

Если операция завершилась ошибкой, действующая редакция и архив не должны оказаться в
промежуточном состоянии.

## 17. Когда нужно повторное принятие

Новое подтверждение обязательно запрашивается при существенном изменении:

- роли Оператора;
- целей или состава обработки персональных данных;
- состава публично распространяемых данных;
- каналов рекламной рассылки;
- передачи данных новым категориям получателей;
- правил оплаты, комиссии или возвратов, если изменения затрагивают уже используемую платную
  функцию;
- условий родительского согласия;
- условий оферты перед новой оплатой или новым платным периодом.

Исправление опечатки сохраняется как новая редакция, но может не требовать отдельного повторного
согласия. Решение фиксируется в поле `requires_reacceptance`.

## 18. Безопасность

- Канонические документы, база согласий и журналы размещаются на российском сервере.
- Сервер не доверяет ключу, версии и хешу только со стороны браузера.
- IP-адрес определяется с учётом доверенного reverse proxy; случайный заголовок клиента не
  принимается как достоверный IP.
- API принятия согласий требует CSRF-защиту, проверку сессии и ограничение частоты запросов.
- Журналы согласий доступны только уполномоченным сотрудникам.
- Сырой HTML из Markdown не исполняется.
- Все административные изменения документов журналируются.
- Резервные копии защищаются и размещаются с учётом требований к локализации персональных данных.
- Секреты, токены отписки и пароли не записываются в Markdown или фронтенд-конфигурацию.

## 19. Что заполняется после открытия ИП или ООО

В текстах и реестре документов заменяются только переменные сведения:

```text
полное и сокращённое наименование
ИНН
ОГРН или ОГРНИП
юридический адрес или адрес регистрации
руководитель либо владелец
банковские реквизиты
контактная почта
дата начала действия
```

Структура страниц, маршруты, API и таблицы базы из-за этого не меняются.

## 20. Что заполняется после покупки сервера и подключения сервисов

В Политику конфиденциальности и её приложения вносятся:

```text
российский хостинг-провайдер
город или регион дата-центра
почтовый сервис
платёжный провайдер
банк и ОФД
видеосервис или собственная инфраструктура видеосвязи
сервис мониторинга ошибок
фактические cookie и ключи локального хранилища
сроки хранения технических журналов
```

Если новый сервис получает персональные данные, до подключения проверяются его место размещения,
договор, поручение на обработку и фактический перечень передаваемых данных.

## 21. Порядок разработки

Рекомендуемая последовательность:

1. Создать серверные каталоги `drafts`, `current` и `archive`.
2. Создать реестр документов и таблицу версий.
3. Создать таблицы событий согласия и текущих состояний.
4. Реализовать API чтения действующего документа.
5. Реализовать единую React-страницу юридического документа.
6. Добавить все маршруты `/legal/...`.
7. Добавить три регистрационные галочки и ссылки.
8. Реализовать серверную фиксацию редакций и действий.
9. Связать рекламное согласие с подтверждением email.
10. Реализовать настройки согласий в Личном кабинете.
11. Реализовать безопасную отписку без авторизации.
12. Добавить список запрета рекламной рассылки.
13. Реализовать отдельное родительское согласие для каждого детского профиля.
14. Реализовать административную публикацию новой редакции.
15. Перенести проверенные тексты из рабочих файлов в производственные Markdown-файлы.
16. После открытия ИП или ООО заполнить реквизиты.
17. После покупки сервера заполнить сведения об инфраструктуре.
18. Провести юридическую, бухгалтерскую и техническую проверку перед публикацией.

## 22. Что нельзя делать

- Нельзя хранить только текущий текст без архива редакций.
- Нельзя заменять опубликованный файл, сохраняя старый номер версии.
- Нельзя считать значение `true` достаточным доказательством согласия без текста, версии и лица.
- Нельзя объединять согласие на рекламу с обязательной регистрационной галочкой.
- Нельзя заранее отмечать галочки.
- Нельзя отправлять рекламу до подтверждения электронной почты.
- Нельзя переносить рекламное согласие на новый email автоматически.
- Нельзя направлять рекламные сообщения непосредственно несовершеннолетнему.
- Нельзя удалять историю отзыва при повторном согласии.
- Нельзя принимать версию и контрольную сумму документа от браузера без серверной проверки.
- Нельзя показывать черновик обычным пользователям как действующий документ.
- Нельзя встраивать реквизиты, секреты или токены непосредственно в React-код.

## 23. Проверка готовности

Перед запуском должно выполняться следующее:

- [ ] Каждый документ открывается по постоянному адресу.
- [ ] Отображаются название, редакция и дата действия.
- [ ] Неизвестный адрес возвращает 404.
- [ ] Все регистрационные галочки изначально пустые.
- [ ] Без обязательных согласий регистрация невозможна.
- [ ] Без рекламного согласия регистрация возможна.
- [ ] Текст рекламной галочки содержит слова «по электронной почте».
- [ ] После регистрации сохранены версии, хеши, текст галочек, дата, IP и браузер.
- [ ] Реклама не отправляется до подтверждения email.
- [ ] Ребёнку не показывается рекламная галочка.
- [ ] Родительское согласие связано с конкретным детским профилем.
- [ ] Отписка работает без входа в аккаунт.
- [ ] После отписки рекламное письмо не отправляется.
- [ ] Служебные письма после рекламной отписки продолжают работать.
- [ ] Смена email приостанавливает старое рекламное согласие.
- [ ] Предыдущая опубликованная редакция доступна в архиве.
- [ ] Новая редакция получает новую контрольную сумму.
- [ ] Черновики недоступны обычному пользователю.
- [ ] База, файлы согласий и журналы находятся на российском сервере.
- [ ] Реквизиты Оператора заполнены во всех опубликованных документах одинаково.
- [ ] Комплект проверен юристом, бухгалтером и техническим специалистом.

## 24. Результат

После выполнения этой инструкции юридические тексты можно добавлять и обновлять как
отдельные Markdown-файлы. React отвечает только за отображение, NestJS — за выбор действующей
редакции и фиксацию действий, а PostgreSQL — за реестр, историю версий и доказательства
согласий. При регистрации эта схема уже реализована модулем `legal-consents`.

Открытие ИП, покупка российского сервера и подключение платёжных сервисов потребуют
заполнения реальных сведений, но не изменения общей архитектуры.
