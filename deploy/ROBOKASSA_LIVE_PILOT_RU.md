# GoStudy: разовая подписка и чеки — ограниченный запуск

Дата пакета: 01.11.2026. Основа: предоставленный архив GitHub с исправлениями от 30.10.
**Установка исходников НЕ включает реальные оплаты.** Это этап подготовки и проверки на одном явно разрешённом аккаунте, не общий запуск монетизации.

## Что меняется

- Отдельная форма реальной оплаты на 30 дней, без рекуррентных списаний.
- Цена только из опубликованного тарифа; выбранные блоки применяются ко всему новому периоду.
- `Receipt`: одна услуга «Доступ к GoStudy на 30 дней, до N учеников», количество 1,
  полная сумма с блоками, `full_prepayment`, `service`, `none`, `usn_income`.
- Боевые/тестовые пароли разделены. Результат с тестовой подписью не подтверждает реальный заказ.
- В заказе сохранены снимки тарифа, чека, подтверждённой почты, полного текста оферты и правил,
  их версий/хешей, времени и метаданных согласия. Изменение тарифа не переписывает заказ.
- Result URL подтверждает оплату атомарно вместе с периодом и заданием итогового чека.
  Success/Fail только возвращают браузер. Повтор Result URL не продлевает период повторно.
- Новый оплаченный период ставится после последнего оплаченного; текущий лимит не меняется.
- В конце периода работник отправляет второй чек `full_payment`, `payments.type=2`, без нового списания.
  Состояние `registered` устанавливается только после ответа Status `Done`.
- Обновлены тексты оферты, правил, оплаты, поддержки и публичного тарифа: разовое продление.
  Старые редакции лежат в `docs/legal-history/2026-10-08`; прежние согласия в БД не меняются.
- После отключения новых оплат Result URL продолжает принимать уведомления по уже выданным счетам.

## Границы этого патча

- **Общий платный барьер и применение лимита учеников к существующим функциям НЕ включены.**
  Периоды и лимиты оплаченных пакетов фиксируются и показываются; работа текущих аккаунтов сохраняется.
  До массового запуска отдельно согласовать переход существующих пользователей и внедрить ограничения.
- Автосписания, доплата за места посреди периода и автоматические возвраты не реализованы.
- Начальный чек запрашивается через Receipt, но `paid` означает подтверждение оплаты, не доказательство
  фискальной регистрации первого чека. Его регистрацию и доставку проверяем в кабинете Robokassa/ОФД.
- Итоговый чек автоматически ставится на окончание периода доступа. Досрочное прекращение/возврат
  требует остановки задания и ручной обработки с бухгалтером; не оставлять такой заказ в обычной очереди.
- При неоднозначной отправке итогового чека повторный Attach автоматически не делается.
  Сначала Status, через 24 часа без определённого результата — `review` и запись ERROR в журнале.
- Налоговые параметры реализуют подтверждённые владельцем настройки. При смене СНО/НДС/схемы оплаты
  сначала менять код и проверять новые чеки. Старые заказы сохраняют собственный снимок.

## Проверки перед активацией

1. Установить патч на локальную копию; сгенерировать Prisma Client, выполнить линтеры, тесты и сборки.
2. Выполнить отдельный PostgreSQL-тест (ниже). Он не обращается в Robokassa.
3. Перечитать изменённые условия и согласовать момент итогового расчёта/порядок возвратов с бухгалтером.
4. Проверить в кабинете Robokassa: магазин `gostudy`, MD5, Робочеки, Предоплата 100%, Услуга,
   УСН (доходы), Без НДС. Проверить статус договора/вывода средств отдельно.
5. Создать и безопасно сохранить отдельные **боевые** Пароль №1 и №2. Не присылать в чат, не коммитить.
6. Настроить мониторинг очереди чеков, регулярное резервное копирование и ответственного за `review`/`held`.
7. Разрешить только согласованный аккаунт (для первоначальной проверки — ID 3); общий доступ не включать.
8. При первой согласованной реальной покупке проверить цену, номенклатуру и отсутствие повторных списаний,
   подпись/серверное подтверждение, период, чек предоплаты в кабинете и его доставку на почту.
9. Проверить регистрацию второго чека через провайдера после фактического оказания услуги.
   Не ускорять реальные сроки в БД ради проверки. Модульные тесты проверяют механику, не связь с кассой.

## Порядок установки на VPS

Команды выполнять **в SSH на gostudy-prod-01**, по одной после проверки предыдущего результата.
Сначала распаковать архив в отдельную временную папку и запускать его установщик оттуда:
`sudo node <папка-патча>/deploy/install-robokassa-live-patch.mjs /srv/gostudy/app`.
Установщик сверяет хеши всех изменяемых файлов до записи, создаёт резервную копию и останавливается
при несовпадении. Не распаковывать с принудительной перезаписью прямо поверх сервера.

Перед миграцией сделать резервную копию БД и проверить `pg_restore --list`.
Установщик не меняет БД, env, nginx, сервисы, загрузки или node_modules.

Из `/srv/gostudy/app`:

```bash
npm run server:prisma:generate
npm run server:lint
npm run server:test
npm --prefix server run test:modules
npm run lint
npm run build
```

Миграцию выполнять под пользователем приложения с production DATABASE_URL через существующий безопасный
механизм окружения: `npm --prefix server run prisma:migrate:deploy`, затем `prisma:status`.
**Не использовать `prisma migrate dev`, `db push`, `migrate reset` на сервере.**
Новая миграция `20261031120000_subscription_live_pilot` добавляет таблицы, сохраняет тестовые записи.
Пока рабочая БД не мигрирована, не перезапускать API на новой сборке.

После успешной миграции/сборок:

```bash
sudo rsync -a --chown=ubuntu:www-data --chmod=D2750,F640 /srv/gostudy/app/dist/ /var/www/gostudy/
sudo systemctl restart gostudy-api
curl -fsS --max-time 10 http://127.0.0.1:3002/api/v1/health
```

Не добавлять `--delete` к rsync: открытым вкладкам могут понадобиться старые хешированные ресурсы.
Юридические документы используются и API, и сборкой; обновляются в рамках одного развёртывания.
Ни один флаг реальной оплаты этим порядком не включается.

## Окружение

Файл `/etc/gostudy/app.env`: сохранять существующие параметры, права root:gostudy 0640.
Это EnvironmentFile systemd: **не выполнять `source /etc/gostudy/app.env`**.
Ниже безопасные начальные значения (пароли отдельно вводятся локально на сервере):

```ini
ROBOKASSA_LIVE_ENABLED=false
ROBOKASSA_LIVE_REVIEWED=false
ROBOKASSA_FISCAL_WORKER_ENABLED=false
ROBOKASSA_LIVE_TEACHER_IDS=
ROBOKASSA_LIVE_PASSWORD1=
ROBOKASSA_LIVE_PASSWORD2=
```

После завершения проверок оператор отдельно включает worker/reviewed/live и задаёт список числовых ID.
Звёздочка не поддерживается. Оба боевых пароля обязательны, должны быть разными и отличаться от тестовых.
MD5 в кабинете должен соответствовать коду. Не ротировать пароли при незавершённых счетах/чеках без плана перехода.
`ROBOKASSA_MERCHANT_LOGIN` общий для двух режимов. Тестовая настройка остаётся независимой.

Экстренно остановить **новые** оплаты: `ROBOKASSA_LIVE_ENABLED=false` и перезапуск API.
Для уже оплаченных периодов оставлять worker и пароли: они нужны для завершения чеков.
Отключение `LIVE_ENABLED` само по себе не аннулирует ранее выданные счета.

## Проверка PostgreSQL без реальных платежей

Сценарий: `server/scripts/check-subscription-postgres.cjs` после `npm run server:build`.
Нужна отдельная база с точным именем `gostudy_subscription_check`; production `gostudy` отклоняется.
Переменная `GOSTUDY_SUBSCRIPTION_TEST_DATABASE_URL` задаётся только в текущей сессии без вывода пароля.

```bash
node server/scripts/check-subscription-postgres.cjs
```

Создаёт случайную схему, минимальную таблицу users, применяет старую тестовую и новую миграции,
проверяет старые тестовые строки, конкурентные callbacks, последовательность периодов,
откат при ошибке фискального задания и конкурентный захват заданий двумя workers.
В конце удаляет **только свою случайную схему**. Gateway заменён заглушкой, внешних платежей/чеков нет.
Если тест не завершился штатно, он пишет сообщение об ошибке без строки подключения.

## Наблюдение и ручная остановка чека

Администратору доступны (обычная авторизация приложения):
- `GET /api/v1/admin/subscription-receipts` — до 100 незавершённых заданий;
- `POST /api/v1/admin/subscription-receipts/:id/hold` — `{ "hold": true, "reason": "Причина обращения" }`;
- тот же endpoint с `hold: false` снимает остановку; действие записывается в аудит.

Остановку нельзя менять во время активной отправки. Повторить после окончания обработки.
Снятие остановки с уже отправленного задания возобновляет **Status**, не отправляет Attach заново.
Для `review` сначала сверить id итогового чека (`2147483648 + job.id`), InvId, сумму и статус в Robokassa.
Если провайдер не получил чек, повторная отправка — отдельное контролируемое действие после выяснения причины;
не сбрасывать вслепую `submitted_at`, не создавать второй job и не менять InvId.

Диагностика БД, только чтение:

```sql
SELECT id, order_id, state, due_at, submitted_at, registered_at, last_code
FROM subscription_receipt_jobs ORDER BY due_at;
SELECT state, count(*) FROM subscription_receipt_jobs GROUP BY state;
```

Регистрация первого чека проверяется отдельно в кабинете. Проблема с фискальным чеком не должна
приводить к новому списанию или повторной выдаче периода.

## Откат

Пока реальных заказов нет: выключить live/worker, вернуть изменённые исходники из резервной копии,
пересобрать API/frontend. Добавленные таблицы можно оставить; обратную миграцию с удалением данных не применять.
После первого реального заказа не возвращать старый test-only обработчик Result URL: он отвергнет реальные
уведомления. Остановить новые оплаты флагом и исправлять вперёд, сохраняя историю и worker чеков.
Не восстанавливать старую БД поверх новых платежей.
